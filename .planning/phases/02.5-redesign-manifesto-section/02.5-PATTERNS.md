## Pattern Assignments

### `src/components/HomepageScrollytelling.tsx` — Manifesto desktop block (component, scroll-driven reveal)

**Analog:** Group 3 stage, same file, lines 964-1056 (and supporting motion-value setup lines 246-248, 511-535)

**Scroll-progress motion value setup** (lines 246-248, 511-520):
```typescript
// Group 3 scroll progress (0→1) as a motion value — drives the drive-scene
// directly from the rAF loop, so scroll animation never re-renders React.
const progressMV = useMotionValue(0);
...
const driveProgress = useSpring(progressMV, { stiffness: 110, damping: 30, mass: 0.7 });

const carXvw = useTransform(driveProgress, [0, 1], [-30, 6]);
const carBobVh = useTransform(driveProgress, [0, 0.45, 0.75, 1], [0.8, -0.5, 0.4, 0]);
const carLeanDeg = useTransform(driveProgress, [0, 0.12, 0.9, 1], [-2.2, 0, 0, 0.5]);
const carTransform = useMotionTemplate`translate3d(${carXvw}vw, ${carBobVh}vh, 0) rotate(${carLeanDeg}deg)`;
```

**Important distinction for the planner:** Group 3's `progressMV` is fed by **horizontal scroll-left ratio inside a horizontal-scrub track** (`g3.scrollLeft / max`, set in the wheel-redirect rAF loop, lines 377-380), NOT by vertical scroll-snap arrival. CONTEXT.md D-08 asks to reuse the "motion-value-tied-to-scroll-position mechanism," but Manifesto is a plain vertical `.scroll-snap-section`, not a horizontal-scrub group like g1/g2/g3. The directly-reusable piece is the **technique** (a `useMotionValue` updated outside React render + `useTransform`/`useMotionTemplate` to derive per-panel scale/opacity/translate), not the literal `g3.scrollLeft` source. The existing **vertical** scroll signal already available is `scrollTop` (state, line 255) and `vh` (state, line 256), updated via the plain scroll listener (lines 349-361):

```typescript
// ── Scroll Listener for scrollytelling state ───────────────────────────────
useEffect(() => {
  const container = containerRef.current;
  if (!container) return;
  const handleScroll = () => {
    setScrollTop(container.scrollTop);
  };
  container.addEventListener('scroll', handleScroll, { passive: true });
  return () => container.removeEventListener('scroll', handleScroll);
}, []);
```

The current (pre-redesign) Manifesto block already derives a manual scroll-driven opacity/transform straight from `scrollTop` and `vh` with **inline style math**, not motion values (lines 736-744):

```typescript
<div
  className="max-w-4xl w-full text-center border border-[var(--pw-border)] p-16 relative overflow-hidden backdrop-blur-md bg-black/5"
  style={{
    opacity: Math.min(1, Math.max(0, (scrollTop - vh * 0.7) / (vh * 0.4))),
    transform: `translateY(${Math.max(0, 40 - ((scrollTop - vh * 0.7) / (vh * 0.4)) * 40)}px)`,
    transition: 'opacity 0.5s ease, transform 0.5s ease'
  }}
>
```

**Recommended approach for the new 3-panel reveal:** Mirror Group 3's `useMotionValue` + `useTransform` + `useMotionTemplate` *technique*, but derive the driving motion value from `scrollTop`/`vh` (the section's own arrival window) via a `useEffect` that calls `.set()` on a dedicated `manifestoProgressMV` whenever `scrollTop` crosses the Manifesto section's vertical offset — same shape as the existing inline-math gate above, just piped through a motion value instead of inline `style` math, so `useTransform` can do the staggered per-panel scale/opacity without per-frame React re-renders. This satisfies D-08 ("tied to scroll-snap arrival... not generic IntersectionObserver") while staying consistent with the codebase's only two existing scroll-driven mechanisms (motion-value rAF for g1-g3, scrollTop-math for the current Manifesto/Hero/About reveal).

**Stagger pattern reference** (per-element `transitionDelay`, used for left-to-right cascading reveal elsewhere in this file, lines 829-855):
```typescript
<CollectionCard product={products[0]} className={`w-full flex-1 min-h-0 reveal-dashboard-item ${activeIndex1 >= 1 ? 'reveal-active' : ''}`} />
<CollectionCard product={products[1]} className={`w-full flex-1 min-h-0 reveal-dashboard-item ${activeIndex1 >= 1 ? 'reveal-active' : ''}`} style={{ transitionDelay: '100ms' } as React.CSSProperties} />
<CollectionCard product={products[2]} className={`w-full flex-1 min-h-0 reveal-dashboard-item ${activeIndex1 >= 1 ? 'reveal-active' : ''}`} style={{ transitionDelay: '150ms' } as React.CSSProperties} />
```
This is the closest existing precedent in the codebase for "staggered left-to-right cascade gated by a single boolean/scroll-derived flag" (D-07). For the 3 Manifesto panels, the same `transitionDelay: 'Nms'` inline-style approach (0ms / 120-150ms / 240-300ms) layered on top of a shared `revealActive` boolean (or the `useTransform`-derived scale/opacity if going the motion-value route) is the most idiomatic match — simpler to implement correctly than three independently-keyframed `useTransform` curves, and the CSS easing (`cubic-bezier(0.16, 1, 0.3, 1)`) is already the project-wide convention (see Shared Patterns below).

**Group 3 JSX structure to model panel layout/markup conventions on** (lines 1001-1007, motion.span with transform style + WM color):
```typescript
<motion.span
  className="g3-wordmark font-display-strict select-none"
  style={{ transform: wordmarkTransform, color: WM.text }}
>
  {aboutHeading}
</motion.span>
```

**Section wrapper convention** (current Manifesto desktop wrapper to be replaced, line 737):
```typescript
<div className="scroll-snap-section relative w-full h-screen flex items-center justify-center px-16 overflow-hidden z-10">
```
The new 3-panel section should keep `scroll-snap-section relative w-full h-screen ... overflow-hidden z-10` (D-09: full 100vh, scroll-snap rhythm preserved) but change the flex layout to a 3-column row (`flex flex-row` with each child `w-[33.333vw] h-full`) and drop `px-16`/`items-center justify-center` centering since panels are full-bleed edge-to-edge per D-10.

**Schema pattern** (lines 341-346):

**Note for the planner:** `page-about.liquid` renders the image directly as an `<img src="{{ ... | image_url }}">` server-side in Liquid — it does NOT pass the URL through a `data-*` attribute into React, because that section has no React mount. `hero-canvas.liquid` is different: it's the root of a React-mounted island (`#homepage-interactive-root`), so the 3 new Manifesto image URLs must follow this repo's `data-*` attribute convention (Analog 2 below) rather than `page-about.liquid`'s direct-render approach. Use `| image_url: width: ...` (not `| img_url`, which is the legacy Liquid filter used only in the products JSON script at line 33) for consistency with the one other `image_picker` use in this codebase.

**Analog 2 — existing `hero-canvas.liquid` data-attribute + text-setting convention** (lines 11-20, schema lines 74-169):

```liquid
data-about-heading="{{ section.settings.about_heading | default: 'ABOUT US' | escape }}"
data-cta-label="{{ section.settings.cta_label | default: 'OUR STORY' | escape }}"
data-stat-1-value="{{ section.settings.stat_1_value | default: 'ZERO' | escape }}"
```
```json
{
  "type": "text",
  "id": "about_heading",
  "label": "About Heading",
  "default": "ABOUT US"
}
```
The 3 new tagline text settings ("THE RACE." / "THE MOMENT." / "YOURS.") should follow this exact `type: text` + `default` shape, added under a new `{"type": "header", "content": "Manifesto — 3-Panel Reveal"}` block (matching the existing `"About Us — Group 3"` header at line 95-97). The 3 new `image_picker` settings should sit alongside them in the same header group, each with `"default"` referencing the 3 supplied source images once they are added to the Shopify asset library (per the unresolved blocker in CONTEXT.md — images must be on disk/in Shopify Files before this schema default can be wired).

**Image URL must be passed via `data-*` attribute** (since `image_picker` settings return a Shopify image object, not a string, the `| image_url` filter must be applied in the liquid attribute itself, e.g.):
```liquid
data-manifesto-image-1="{% if section.settings.manifesto_image_1 != blank %}{{ section.settings.manifesto_image_1 | image_url: width: 1600 }}{% endif %}"
```
This mirrors the existing `data-wordmark-footer-url="{{ 'wordmark-footer.png' | asset_url }}"` pattern at line 21 (a pre-resolved URL string baked into a `data-*` attribute), just swapping `asset_url` for `image_url` since the source is a schema image picker rather than a static theme asset.
