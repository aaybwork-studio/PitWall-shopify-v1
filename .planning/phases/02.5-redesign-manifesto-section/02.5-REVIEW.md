# Phase 02.5: Code Review Report

**Reviewed:** 2026-06-19T00:00:00Z
**Depth:** standard
**Files Reviewed:** 4
**Status:** issues_found

## Summary

Reviewed the Manifesto section redesign (3-panel image reveal) across the Liquid section, bootstrap wiring, the main scrollytelling component, and global stylesheet. The Liquid template correctly escapes tagline text and image URLs are server-generated (no injection risk there). The main correctness issue is that the manifesto panel images have no fallback/placeholder when a merchant has not configured an image, which will render visibly broken `<img>` elements with empty `src` on both desktop and mobile layouts. There are also several pre-existing quality issues in the surrounding code (duplicate line, dead motion values, missing `alt` text, footer DOM reparenting without guard against duplicate mounts) that are now more visible in this section's diff context per the file list provided.

## Critical Issues

### CR-01: Manifesto panel images render with empty `src` when not configured in theme editor

**File:** `src/components/HomepageScrollytelling.tsx:758,762,766,591,595,599`
**Issue:** `manifestoImage1/2/3` default to `''` (empty string) when the merchant has not picked an image in the theme editor (see `sections/hero-canvas.liquid:22-24`, which emits `data-manifesto-image-N=""` when `section.settings.manifesto_image_N` is blank). The component then renders:
```jsx
<img className="absolute inset-0 w-full h-full object-cover" src={manifestoImage1} alt="" loading="lazy" />
```
An `<img>` with `src=""` is not a no-op in browsers — many browsers will issue a request to the current document URL (re-requesting the page itself) and/or fire a console error, and the image will render as a broken/empty box where the tagline text is the only content. Since this is the first content section users see after the hero (both desktop and mobile), an unconfigured Manifesto panel (which is the out-of-the-box state for any new theme install, since none of the three `image_picker` schema settings have defaults) will look broken by default, not just degraded.
**Fix:** Add a fallback image/placeholder and guard the empty case, e.g.:
```jsx
{manifestoImage1 && (
  <img className="absolute inset-0 w-full h-full object-cover" src={manifestoImage1} alt="" loading="lazy" />
)}
{!manifestoImage1 && <div className="absolute inset-0 w-full h-full bg-[#0F0C09]" />}
```
or supply a bundled placeholder asset URL as the JS-side default (mirroring how `video_1`/`video_2`/`video_3` already fall back to bundled asset URLs in the Liquid template at lines 5-9).

## Warnings

### WR-01: Manifesto images and taglines have no accessible text alternative

**File:** `src/components/HomepageScrollytelling.tsx:591,595,599,758,761,765`
**Issue:** All six manifesto `<img>` tags (3 desktop + 3 mobile) use `alt=""`. The overlaid tagline (`THE RACE.`, `THE MOMENT.`, `YOURS.`) is purely decorative text rendered with `mixBlendMode: 'difference'` and is not tied to the image's content. A screen reader user gets no information about these three full-bleed panels at all — not even the tagline, since it's rendered as a `<span>` with no semantic relationship to the image.
**Fix:** Use the tagline (or a merchant-configurable alt field) as the image's `alt` text, or mark the images `alt=""` intentionally only if the tagline `<span>` is understood by AT as the equivalent text — but currently neither path is true. At minimum: `alt={manifestoTagline1}` so the content is announced.

### WR-02: Duplicate, dead-weight `motion.div`/`useTransform` definitions for manifesto panel reveal

**File:** `src/components/HomepageScrollytelling.tsx:268-272`
**Issue:**
```js
const manifestoPanelOpacity = useTransform(manifestoProgressMV, [0, 0.6], [0, 1]);
const manifestoPanelScale = useTransform(manifestoProgressMV, [0, 0.6], [0.88, 1]);
void manifestoPanelOpacity; void manifestoPanelScale;
```
These two `useTransform` motion values are created on every render and then immediately discarded via `void`. They serve no purpose — the actual reveal animation is driven entirely by the `reveal-active` CSS class toggle. This is unused code creating two motion-value subscriptions per render for no behavior.
**Fix:** Remove these two lines entirely; they are confirmed dead per the comment directly above them ("the panel reveal itself uses the simpler CSS .manifesto-panel/.reveal-active class pair").

### WR-03: Duplicate statement in `openMenu()`

**File:** `src/main.tsx:240-241`
**Issue:**
```js
if (menuTrigger) menuTrigger.innerText = 'CLOSE';
if (menuTrigger) menuTrigger.innerText = 'CLOSE';
```
Line 241 is an exact duplicate of line 240 — harmless but indicates a copy-paste artifact left in code that ships.

### WR-04: Footer DOM node reparented without checking it isn't already correctly placed, and a second mount could double-move it

**File:** `src/components/HomepageScrollytelling.tsx:319-334`
**Issue:** The effect unconditionally calls `scrollContainer.appendChild(footer)` / `document.body.appendChild(footer)` on every `isMobile` change, and on cleanup always moves it back to `document.body`. Because `appendChild` on an already-attached node performs a move, this is not itself a crash risk, but combined with `React.StrictMode` (which double-invokes effects in development, see `main.tsx:81`), the footer element will be moved to `containerRef.current`, then back to `document.body` (cleanup), then back to `containerRef.current` again on every dev re-render — this is harmless in prod (`StrictMode` only double-invokes in dev) but means dev behavior diverges from prod and can mask reparenting bugs during development.
**Fix:** Not blocking, but worth guarding with an identity check (`if (footer.parentElement !== scrollContainer) scrollContainer.appendChild(footer)`) to avoid redundant DOM moves and make the effect idempotent/StrictMode-safe.

### WR-05: `img_url` filter usage may be deprecated in favor of `image_url`

**File:** `sections/hero-canvas.liquid:39`
**Issue:** `{{ product.featured_image | img_url: '600x' | json }}` uses the legacy `img_url` filter, while the manifesto images two settings groups below correctly use the modern `image_url: width: 1600` filter (lines 22-24). Shopify has deprecated `img_url` in favor of `image_url` for new theme development; mixing both in the same file is an inconsistency that risks future breakage if `img_url` is removed.
**Fix:** Standardize on `image_url`: `{{ product.featured_image | image_url: width: 600 | json }}`.

### WR-06: `getSlideIndex` assumes non-empty `groupEl.children` and a single sizing pass; can mis-detect index for first slide group due to lack of explicit empty-array guard

**File:** `src/components/HomepageScrollytelling.tsx:160-169`
**Issue:** If `groupEl.children` is empty (e.g., a future group with zero static slides at mount before the dynamic product list renders), the loop never executes and `slides.length - 1` returns `-1`. This value is then used as a comparison against `activeIndex1 >= 1` elsewhere (e.g. line 510, 827) — an index of `-1` will satisfy `activeIndex1 === 0` checks incorrectly is not literally true here (it returns `-1`, not `0`), but it silently produces a nonsensical negative active index rather than failing loudly, which would manifest as collection-grid reveal items never activating (`-1 >= 1` is false) without any error surfaced.
**Fix:** Guard for the empty case explicitly: `if (slides.length === 0) return 0;` at the top of the function, and/or assert `groupEl.children.length > 0` defensively given this is reachable from a live DOM ref.

## Info

### IN-01: `void` pattern used to silence unused-variable lint warnings for props that are intentionally still accepted but unused

**File:** `src/components/HomepageScrollytelling.tsx:217-220`
**Issue:**
```js
void stat1Value; void stat1Label; void stat2Value; void stat2Label; void stat3Value; void stat3Label;
```
This is a reasonable stopgap to keep the props in the type signature (for backward Liquid-schema compatibility) while suppressing unused-variable lint noise, and the comment above explains why. Flagging only because it is a slightly unusual pattern that a future maintainer might not recognize as intentional without reading the comment closely.
**Fix:** No action required; comment is sufficient. Consider removing the props from `HomepageScrollytellingProps` and `main.tsx` entirely in a follow-up cleanup phase once schema is also pruned, to avoid the dead parameter surface growing further.

### IN-02: Magic timing/threshold constants scattered through scrollytelling logic without named constants

**File:** `src/components/HomepageScrollytelling.tsx:390-391,442,452,467,473`
**Issue:** Values like `vh * 0.7`, `vh * 1.3`, `0.92`, `0.5`, `0.4`, `0.32` are inlined directly in scroll-progress and lerp calculations with only prose comments nearby. This makes it harder to tune behavior consistently if these numbers need to change together.
**Fix:** Extract to named constants (e.g., `MANIFESTO_REVEAL_START_VH = 0.7`, `G3_INTERSECTION_ENGAGE = 0.92`, `G3_LERP_FACTOR = 0.32`) for readability; non-blocking style improvement.

### IN-03: `.car-silhouette` and `.manifesto-video-strip` CSS classes appear unused by the reviewed components

**File:** `src/index.css:735-744,869-883`
**Issue:** `.car-silhouette` and `.manifesto-video-strip` are defined (and have mobile media-query overrides at lines 916-921, 908-915) but neither class name appears anywhere in `HomepageScrollytelling.tsx`. This looks like leftover CSS from a prior iteration of the Manifesto/Group-3 design that was superseded by `.g3-car` and the inline video elements at lines 654-660/863-869 of the TSX.
**Fix:** Remove the dead CSS rules (and their media-query overrides) once confirmed unused elsewhere in the codebase, to reduce stylesheet bloat and avoid confusing future maintainers about which classes are live.

### IN-04: Empty-string fallback for manifesto images chosen over a documented bundled placeholder asset, unlike the video playlist pattern

**File:** `sections/hero-canvas.liquid:22-24` vs `5-9`
**Issue:** The video playlist settings (`video_1`/`video_2`/`video_3`) each have an explicit Liquid `{%- if ... != blank -%}...{%- else -%}<bundled asset>{%- endif -%}` fallback pattern, but the three manifesto image settings have no equivalent fallback — they just conditionally emit the URL or nothing. This inconsistency in pattern is the root cause of CR-01.
**Fix:** Apply the same `{%- if ... != blank -%}...{%- else -%}{{ 'manifesto-placeholder-N.jpg' | asset_url }}{%- endif -%}` pattern used for videos, once placeholder assets are added.

### IN-05: `manifestoRevealed` state is desktop-only; mobile manifesto panels are unconditionally given `reveal-active`

**File:** `src/components/HomepageScrollytelling.tsx:590,594,598` vs `757,761,765`
**Issue:** On mobile, all three manifesto `<section>` elements are hardcoded with the `reveal-active` class (no scroll-triggered animation), while desktop uses the `manifestoRevealed` state plus staggered `transitionDelay`. This is presumably an intentional simplification for mobile (no scroll-progress tracking needed for a simple vertical stack), but it means the "staggered scale-up-from-center reveal" entrance effect described in the CSS comment (`index.css:1290`) never plays on mobile — panels are simply visible immediately on mount with no animation at all.
**Fix:** If parity is desired, drive mobile panels off an `IntersectionObserver` per-panel; otherwise, no action needed if mobile-static is the intended design — but confirm this is a deliberate decision rather than an oversight, since nothing in the code comments documents it.
