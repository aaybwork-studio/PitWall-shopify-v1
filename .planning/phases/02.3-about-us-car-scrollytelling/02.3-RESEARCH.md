## 1. ESPN Scroll Pattern

**How the ESPN McLaren car animation works (pattern analysis):**

The ESPN feature article uses a `position: sticky` + `translateX` technique driven by the document's vertical scroll position. The car element is sticky within a tall scroll container. As the user scrolls down through the container's height, a scroll listener calculates `scrollY / containerHeight` as a 0→1 progress value and maps it to `translateX` from `100vw` (off-screen right) to a resting position.

This is scroll-driven `translateX` tied to scroll progress — the same pattern as D-03. The key difference from this project: ESPN uses vertical scroll as the driver; this project uses `group3Ref.current.scrollLeft` as the driver (matching the existing ticker offset pattern in the codebase).

**Applicable insight:** The car position formula is:
```
progress = group3.scrollLeft / (group3.scrollWidth - group3.clientWidth)  // 0 → 1
carX = startX + progress * (endX - startX)
```
where `startX` is off-screen left (`-30vw` or similar) and `endX` is the final stopped position (e.g., `5vw` or a fixed pixel offset).

[ASSUMED] The ESPN article itself is behind a wall that changes periodically — the technical pattern is inferred from the ESPN `position:sticky` + scroll-progress animation pattern widely documented in the web animation community, consistent with the decision text in CONTEXT.md D-03 which says "same scroll-position-to-transform pattern as the ESPN reference."

## 3. Car SVG Approach

**Recommendation: Inline JSX SVG component.**

**Why inline SVG wins here:**
- Vite 5 (installed: `"vite": "^5.2.11"`) does NOT include `vite-plugin-svgr` in this project's `devDependencies` [VERIFIED: package.json]. There is no `@svgr/rollup` or `vite-plugin-svg` configured in `vite.config.ts` [VERIFIED: vite.config.ts].
- Importing an SVG file as a React component (`import CarSVG from './car.svg?react'`) requires `vite-plugin-svgr` which is not installed.
- Importing as a URL (`import carUrl from './car.svg'`) and using `<img src={carUrl}>` works without plugins but loses the ability to control fill color via CSS/props — problematic for theming.
- Inline JSX SVG: zero build config, full color control via `fill` prop, no new dependencies.

**Inline SVG approach:**
```typescript
function F1CarSilhouette({ color = '#EDE8E0' }: { color?: string }) {
  return (
    <svg
      viewBox="0 0 800 200"
      xmlns="http://www.w3.org/2000/svg"
      style={{ width: '100%', height: '100%' }}
      fill={color}
      aria-hidden="true"
    >
      {/* path data here */}
    </svg>
  );
}
```

**Aspect ratio:** A side-profile F1 car is roughly 4:1 to 5:1 (length:height). Viewbox `0 0 800 200` is appropriate. The rendered size on screen should be approximately `min(50vw, 600px)` wide × proportional height, placed in the lower half of the panel. The car element needs `position: absolute` and `transform: translateX()` applied via inline style.

**Color:** Use `WM.text` (`#EDE8E0`) as default fill for a pale silhouette on dark background. D-12 permits white or dark-charcoal.

**F1 car silhouette path guidance (key shapes):**
The planner should generate a simplified F1 side-profile SVG with these elements:
- Long low body (`rect` or `path` for main chassis)
- Front wing (flat horizontal extension with endplates)
- Rear wing (vertical T-shape)
- 2 wheels (ellipses — front and rear)
- Cockpit bump (raised section mid-body)
- Sidepods (bulges on either side of cockpit)
- Halo (thin arc above cockpit)

A simplified geometric version using basic SVG shapes is preferable to an intricate path for a placeholder that will be replaced.

## 4. Car Animation Formula

**Verified pattern from existing codebase (ticker uses same principle):**

The ticker uses `tickerOffset` state updated via `setTickerOffset` → `transform: translate3d(${offset}px, 0, 0)`. Group 3's car animation uses the same read-from-DOM-and-apply-transform pattern, but driven by `scrollLeft` instead of an rAF timer.

### Scroll listener approach

The existing `handleScroll` listener on `containerRef` updates `scrollTop` state. A parallel scroll listener on `group3Ref` updates `group3ScrollLeft`:

```typescript
const group3ScrollListener = () => {
  if (group3Ref.current) {
    setGroup3ScrollLeft(group3Ref.current.scrollLeft);
  }
};
group3Ref.current.addEventListener('scroll', group3ScrollListener, { passive: true });
```

However, `group3Ref.current.scrollLeft` is also mutated directly by the wheel handler (same as `g1.scrollLeft = ...`). Updating state from the scroll listener ensures React re-renders the car position.

### Formula

```typescript
const group3MaxScroll = group3Ref.current
  ? group3Ref.current.scrollWidth - group3Ref.current.clientWidth
  : 1;

// 0 → 1 progress across all 3 panels
const carProgress = group3ScrollLeft / Math.max(1, group3MaxScroll);

// Car starts 110% off-screen left, ends at ~8vw from left (just left of text column)
// Using viewport units baked into pixel values at render time is brittle; use vw strings
const carStartX = -30; // vw — off-screen left
const carEndX = 6;    // vw — resting position in Panel 3

const carX = carStartX + carProgress * (carEndX - carStartX);
// Result: a number in vw units
```

Applied as:
```typescript
style={{ transform: `translateX(${carX}vw)` }}
```

**Easing:** The car moves linearly with scroll by default. For a "decelerating stop" feel in Panel 3 (D-06), apply a mild ease curve by transforming `carProgress` through a power function:
```typescript
const easedProgress = 1 - Math.pow(1 - carProgress, 1.5); // ease-out
const carX = carStartX + easedProgress * (carEndX - carStartX);
```

**Panel-specific motion tuning:** With 3 panels (scrollWidth ≈ 3 × 100vw), Panel 1 occupies progress 0→0.33, Panel 2: 0.33→0.67, Panel 3: 0.67→1.0. No per-panel clamping needed — the linear/eased formula already places the car correctly at the boundaries.

**Performance:** Apply `will-change: transform` to the car element. Do NOT use `transition` on the car during scroll — it creates lag. Only remove `will-change` if the page idle detector fires.

## Common Pitfalls

### Pitfall 1: Group 2 Exit Condition Still Returns Without Snap

**What goes wrong:** The current line `if (e.deltaY > 0 && curScroll >= maxScroll - 2) { return; }` inside the Group 2 block lets the container scroll naturally past Group 2. If this is not changed to snap to `g3Top`, the user will scroll past Group 3 entirely without triggering the horizontal intercept.

**How to avoid:** Change the Group 2 exit to `container.scrollTo({ top: g3Top, behavior: 'smooth' }); return;`

**Warning signs:** Scrolling fast through Group 2's last slide goes straight to the footer without stopping at Group 3.

### Pitfall 2: Vertical Snap Conditions Don't Account for Group 3

**What goes wrong:** The existing "Scrolling up from footer/Group 2 bottom" snap condition (line 344) will intercept scrolling up from the vertical stats section and snap to `g2Top` instead of `g3Top`, skipping Group 3 entirely on the way back up.

**How to avoid:** Replace the existing bottom snap condition with the three new conditions described in Section 8.

**Warning signs:** Scrolling up from the footer goes to Group 2, bypassing Group 3.

### Pitfall 3: Car Position Derived from Stale scrollLeft

**What goes wrong:** If `group3ScrollLeft` state is only updated from the scroll event on `group3Ref`, but the wheel handler mutates `g3.scrollLeft` directly (bypassing a scroll event in some browsers), the car position can lag or not update.

**How to avoid:** Add both a scroll event listener on `group3Ref` AND read `g3.scrollLeft` in the `handleScroll` callback on `containerRef` (which fires on every frame when the container scrolls). Actually, the safest approach: update `group3ScrollLeft` directly in the wheel handler after each `g3.scrollLeft =` assignment, not just from the passive scroll event.

### Pitfall 4: `data-*` Attribute Escaping for Multi-Sentence Text

**What goes wrong:** Liquid's `| escape` filter converts `"` to `&quot;` and `'` to `&#39;`. `getAttribute()` in JavaScript returns the unescaped string. However, if `founding_story` contains newlines, they collapse to spaces in HTML attributes — acceptable for short paragraphs.

**How to avoid:** Use a `<script type="application/json" id="about-content-data">` tag instead of `data-*` for multi-sentence text fields (`founding_story`, `brand_paragraph`). This is cleaner for longer text and avoids any escaping edge cases.

### Pitfall 5: `group3Ref` Not Mounted When Wheel Handler Runs

**What goes wrong:** The wheel handler `useEffect` runs once (dependency `[isMobile]`). If `group3Ref.current` is null at that point (e.g., the component re-renders and the ref isn't yet set), the `if (!g1 || !g2 || !g3) return;` guard silently exits, breaking all scroll behavior.

**How to avoid:** The existing pattern reads refs inside the event handler (not in the effect setup), so the ref is always read at call time. Group 3 follows this exact same pattern — `g3 = group3Ref.current` inside the handler function, not outside. This is already safe.

### Pitfall 6: `will-change: transform` Left On Permanently

**What goes wrong:** `will-change: transform` promotes the element to its own compositing layer, consuming GPU memory. If left on permanently for the car element (even when off-screen or post-scroll), it wastes resources on mobile.

**How to avoid:** Apply `will-change: transform` only when Group 3 is the active zone (i.e., when `isAtG3`). Track this with a state variable `const [g3Active, setG3Active] = useState(false)` and set it in the wheel handler.
