# Phase 02.3: Code Review Report

**Reviewed:** 2026-06-07T00:00:00Z
**Depth:** standard
**Files Reviewed:** 6
**Status:** issues_found

## Summary

Reviewed the Group 3 "About Us" car scrollytelling addition, the wheel-event state machine, the `carX` animation formula, Shopify schema fields, and cleanup behavior of new effects. The wheel handler is large and has several reachable dead/contradictory branches resulting from merge-conflict resolution (notably the Group 2 → Group 3 transition and the post-Group-3 "snap-assist" rules being unreachable in practice). The `carX` formula reads `group3Ref.current` directly during render without subscribing to a resize/layout-change signal, which can produce stale or zero-division-adjacent values on first paint and after layout shifts. `assets/main.css` appears to be a generated/minified bundle checked into source — it should not be hand-reviewed/maintained as source, and its presence in the diff is suspicious for a frontend-only phase. Several smaller issues (variable shadowing, magic numbers, missing dependency tracking) are noted below.

## Critical Issues

### CR-01: `carX` derived directly from `group3Ref.current` during render — stale/zero values and missed re-renders

**File:** `src/components/HomepageScrollytelling.tsx:586-591`
**Issue:** `group3MaxScroll` and therefore `carX` are computed by reading `group3Ref.current.scrollWidth/clientWidth` inline during the render function body:
```js
const group3MaxScroll = group3Ref.current
  ? group3Ref.current.scrollWidth - group3Ref.current.clientWidth
  : 1;
```
On the very first render(s), `group3Ref.current` is `null` (ref not yet attached), so `group3MaxScroll` falls back to `1` and `carX` is computed from a meaningless ratio (`group3ScrollLeft / 1`), causing the car to potentially render far off its intended track on first paint before any scroll occurs. Additionally, `scrollWidth`/`clientWidth` are read directly from the DOM during render — these values can change due to window resize, font loading, or image loading (layout shift) without triggering a re-render, since neither is reactive state. The component has no `ResizeObserver` or `resize`-driven recomputation tied to `group3Ref`, so `carX` can become stale relative to the actual scrollable width after a viewport resize (the existing `resize` handler at line 266-274 only updates `isMobile`/`vh`, not `group3MaxScroll`).
**Fix:** Track `group3MaxScroll` as state, recomputed via a `ResizeObserver` (or recalculated inside the `resize` handler and on mount once the ref is attached):
```js
const [group3MaxScroll, setGroup3MaxScroll] = useState(1);
useEffect(() => {
  const el = group3Ref.current;
  if (!el) return;
  const update = () => setGroup3MaxScroll(Math.max(1, el.scrollWidth - el.clientWidth));
  update();
  const ro = new ResizeObserver(update);
  ro.observe(el);
  return () => ro.disconnect();
}, []);
```

### CR-02: Generated/minified bundle `assets/main.css` checked into source and included in review scope

**File:** `assets/main.css:1`
**Issue:** This file is a single-line, fully minified Tailwind output bundle (38KB+ on one line) — it is a build artifact, not hand-written source. Committing generated CSS directly into `assets/` (rather than producing it via a build step at deploy time) means:
1. Any manual edits to it will be silently clobbered by the next build, creating a maintenance trap.
2. Diff review of "changes" to this file is meaningless/unreviewable (a single massive line), hiding any accidental content changes.
3. If this file is meant to be the production stylesheet shipped to the theme, it should be generated by CI/build pipeline and excluded from the PR diff (or reviewed via its source `index.css` only), not hand-merged.
**Fix:** Add `assets/main.css` (and any other generated bundle outputs) to `.gitignore` / build-output exclusion, and ensure the Shopify theme build step regenerates it from `src/index.css`. If it must be committed (e.g., Shopify CLI requires committed assets), document that it is generated and should never be directly edited, and exclude it from code-review diffs going forward.

## Warnings

### WR-01: Group 2 → Group 3 wheel transition relies on fragile `currentIdx` distance check that can desync from the explicit `g3` lock branch

**File:** `src/components/HomepageScrollytelling.tsx:450-490`
**Issue:** When scrolling down past the end of Group 2 (`currentIdx === 4`, line 450-455), the code calls `snapTo(sections[5])` to jump to Group 3. However the "Group 3 Horizontal Lock" branch (line 460) is gated on `Math.abs(currentScrollTop - g3Top) < 10` rather than `currentIdx === 5`, while the `sections` distance-matching loop (lines 384-390) could pick `currentIdx === 4` or `currentIdx === 6` depending on exact pixel position during the smooth-scroll animation triggered by `snapTo`. During the ~700ms `isSnapping` window this is masked by `e.preventDefault()` at the top of `handleWheel` (line 353-356), but once `isSnapping.current` resets to `false` via the `setTimeout` (line 347-349), if the smooth scroll hasn't fully settled (e.g., on a slow device or with reduced-motion), wheel events can race between the "approaching G3" snap-assist (line 533-537) and the direct G3 lock (line 460), producing visible scroll jitter or an unintended re-snap.
**Fix:** Use the computed `currentIdx` consistently for the Group 3 lock check (`currentIdx === 5`) instead of mixing it with a raw pixel-distance check, so the state machine has one source of truth for "which section am I in":
```js
if (currentIdx === 5) {
  // ... existing G3 lock logic, drop the redundant `Math.abs(...) < 10` gate
}
```

### WR-02: Snap-assist branches at lines 533-551 are unreachable / redundant given the explicit `currentIdx` branches above them

**File:** `src/components/HomepageScrollytelling.tsx:532-551`
**Issue:** These three "snap-assist" blocks attempt to handle scrolling near Group 3 boundaries, but by the time execution reaches them, every `currentIdx` value (0 through 6) has already been handled by an earlier `return` (lines 393, 426, 460, 493, 504, 513, 524) — every branch from 0-6 either returns or falls through only when no condition inside it matched (and even then, those inner blocks `return` unconditionally at their end, e.g. line 489, 509, 520, 529). Tracing the control flow: any `currentScrollTop` maps to exactly one `currentIdx` in `[0..6]`, and each of those 7 values is fully handled with a `return` before reaching line 532. This dead code is a strong signal of a botched merge-conflict resolution (parallel plans both implementing similar "snap toward Group 3" logic).
**Fix:** Remove lines 532-551 entirely, or — if they were intended to catch intermediate `currentScrollTop` values that don't closely match any `sections[i]` (e.g., during fast flicks that skip a whole section) — restructure the `currentIdx` matching to fall through to these assists rather than returning unconditionally from every branch. Trace through with a concrete fast-flick scenario to confirm intended behavior, then either delete or properly wire this code in.

### WR-03: Local `vh` shadows outer `vh` state variable inside `handleWheel`

**File:** `src/components/HomepageScrollytelling.tsx:365`
**Issue:** `const vh = container.clientHeight;` shadows the component-level `const [vh, setVh] = useState(window.innerHeight)` (line 256). While functionally the values are usually equal, this shadowing is confusing for future maintainers (it's not obvious which `vh` is in scope at any given line within this large 220-line handler), and if `container.clientHeight` ever differs from `window.innerHeight` (e.g., scrollbar reservation, mobile browser chrome resize), behavior will silently diverge from what a reader expects from the state variable of the same name.
**Fix:** Rename the local to something distinct, e.g. `const viewportH = container.clientHeight;`, and use that throughout the handler.

### WR-04: `getSlideIndex` heuristic (`scrollLeft < acc + w * 0.6`) duplicated three times with no shared constant

**File:** `src/components/HomepageScrollytelling.tsx:159-169, 403, 409, 436, 442, 470, 477`
**Issue:** The magic threshold `0.6` (60% of slide width) used to decide which slide is "active" is buried in `getSlideIndex` and invoked identically for all three horizontal groups. If this threshold needs tuning (a likely future request, since "active slide" detection drives reveal animations and featured-product swaps), a maintainer must remember it lives in one shared helper — that's fine — but the function itself has no named constant or comment explaining why `0.6` was chosen, making the heuristic feel arbitrary.
**Fix:** Extract `const SLIDE_ACTIVE_THRESHOLD = 0.6;` near the function with a short comment on why 60% was chosen (e.g., "slide considered active once 60% scrolled past, to pre-trigger reveal animations").

### WR-05: `e.deltaY * 0.85` scroll multiplier is a magic number repeated 6 times across the three group-lock branches

**File:** `src/components/HomepageScrollytelling.tsx:402, 408, 435, 441, 469, 476`
**Issue:** The wheel-to-scrollLeft conversion factor `0.85` is hardcoded identically in all six horizontal-scroll update sites (Group 1 ×2, Group 2 ×2, Group 3 ×2). This is a tuning constant that affects perceived scroll "feel" — duplicating it six times means any future adjustment requires six synchronized edits, and a partial edit (missing one site) would silently produce inconsistent scroll speed between groups.
**Fix:** Extract `const WHEEL_SCROLL_MULTIPLIER = 0.85;` at the top of the effect and reference it in all six call sites.

## Info

### IN-01: `group3MaxScroll` fallback of `1` produces a non-zero `rawProgress` even when `group3ScrollLeft` is `0` and `group3Ref.current` is `null`

**File:** `src/components/HomepageScrollytelling.tsx:586-591`
**Issue:** When `group3Ref.current` is `null`, `group3MaxScroll` is `1`, so `rawProgress = 0 / 1 = 0`, `easedProgress = 0`, `carX = -30`. This happens to be the "correct" off-screen-left resting position, so the visual bug is masked in the common case — but it's coincidental, not designed (see CR-01 for the underlying issue). Worth noting this "lucky" cancellation so a future refactor doesn't break it silently.
**Fix:** Addressed by the CR-01 fix (state-driven `group3MaxScroll` initialized to `1` makes the same math explicit and intentional).

### IN-02: `padded.push` while loop in `products` memo can loop indefinitely if `resolvedList` ever becomes empty mid-loop

**File:** `src/components/HomepageScrollytelling.tsx:221-228`
**Issue:** The `while (padded.length < 10)` loop pushes either `resolvedList[i % resolvedList.length]` or a hardcoded fallback object. `resolvedList.length` is checked once per iteration via the ternary (`resolvedList.length > 0 ? ... : ...`), so this is actually safe — `resolvedList` is immutable within the loop. However, the logic is convoluted: it would be clearer to special-case the empty-list scenario once before the loop rather than re-checking `resolvedList.length > 0` on every iteration.
**Fix:** Hoist the empty check:
```js
if (resolvedList.length === 0) {
  while (padded.length < 10) padded.push({ title: 'PITWALL CHASSIS', ... });
} else {
  while (padded.length < 10) padded.push(resolvedList[i++ % resolvedList.length]);
}
```

### IN-03: Inline SVG telemetry waveform in Panel 2 uses raw numeric coordinate lists with no semantic naming or comments explaining the data source

**File:** `src/components/HomepageScrollytelling.tsx:1029-1041`
**Issue:** The `points="0,540 200,480 320,600 ..."` attributes are hardcoded magic-number coordinate lists representing decorative "telemetry" visuals. There's no indication of where these values came from (randomly generated? designed in Figma? meant to represent real telemetry shape?), making future edits (e.g., "make the waveform busier") guesswork.
**Fix:** Add a short comment above each `<polyline>` noting it's purely decorative/arbitrary (e.g., `{/* Decorative waveform — arbitrary coordinates, purely aesthetic */}`) so future maintainers don't assume there's underlying data semantics to preserve.
